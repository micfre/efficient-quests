# Offline tests

Run these commands from the repository root. You need Lua 5.1 and luacheck. If your machine has neither, Docker can run the same commands. The commands use the interpreter name `lua5.1`. Use the name of your own Lua 5.1 interpreter if it differs.

```sh
lua5.1 tests/runtime.lua
lua5.1 tests/saveddata.lua
lua5.1 tests/queststate.lua
lua5.1 tests/characterstore.lua
lua5.1 tests/datastore.lua
lua5.1 tests/routeplanner.lua
lua5.1 tests/stepmodel.lua
lua5.1 tests/followmode.lua
lua5.1 tests/questiefallback.lua
lua5.1 tests/options.lua
lua5.1 tests/menu.lua
lua5.1 tests/stepwindow.lua
lua5.1 tests/lookadapter.lua
lua5.1 tests/tomtombridge.lua
lua5.1 tests/commands.lua
lua5.1 tests/manifest.lua
luacheck dist/EfficientQuests
```

The Lua tests load the addon files and simulate the game services. Each suite loads the addon through the shared `tests/addon.lua` loader, which runs the files in the TOC's order, starting with the embedded libraries, and hands every file the same private namespace, the way the game does. Every suite remains individually runnable. The `runtime` suite covers the entry point: the addon table, the saved-data setup on login, and the one message that a player on another client flavor gets, because the addon supports the Forever client only. The `saveddata` suite covers the two saved tables: the defaults after a fresh login, the split between the account-wide table and the per-character table, and the promise that keys from the old plugin era are left alone instead of being migrated. The `queststate` suite covers the quest state reader: the level, the race, the class, and the faction of the player, the quest log with its objective counts, the completed quests, the player position through the embedded HereBeDragons, and the change callbacks that fire when a quest is accepted, progresses, completes, is handed in, or is abandoned, and when the player levels up. The `characterstore` suite covers the three stores of one character: the skip list with its skip and restore actions, the abandoned quests, and the Follow mode switch. It also checks that a quest taken again leaves the abandoned list, and that two characters keep their state apart. The `datastore` suite covers the copied Trailwright tables: the loader stays quiet when they are well formed, it reports exactly one clear message for a missing or a malformed table, the addon keeps running without the guides that need the broken table, and the data snapshot identity is there for the status command. The `routeplanner` suite covers the route planner: every filter in order (finished quests, race and class, grey quests, abandoned quests, the skip list), the join point by level, the near hand-in rule with true yard distances, the "Level up to N" step, the quests from the log that stay on the route, the rule that a quest just accepted gets no pick-up step, and the wiring that records an abandoned quest through the callback of the reader. Each scenario loads the code modules by hand into a namespace with its own small quests and Path, the way the `datastore` suite breaks its tables on purpose. The `stepmodel` suite covers the step model: the headline of every step kind, the goal lines with their ticks and their counts, the tips and the place notes under the talk lines, the place text with the zone name and the direction, the reward hover data, the hunts block with its 700-yard limit and its cap of three members, the rule that no block appears inside an instance, and the step of one quest for Follow mode, which never becomes a pick-up for a quest that sits in the log. The scenarios load the code modules by hand as well, and the last part builds steps from the real copied tables through the shared loader. The `followmode` suite covers the Follow mode controller: the switch that persists per character, the pick in the quest log through the client's super tracking and through the manual pick hook when the client has none, the step of a quest that is not on the route, the rule that a quest just accepted never becomes a pick-up step, the notifications that keep the served step fresh, the hand-in of the picked quest that ends the following, and the click on the step that returns to the route. The last part follows a quest of the real copied tables through the shared loader. The `questiefallback` suite covers the QuestieDB fallback and the lookup seam: the data store answers the reader's name and position questions from the copied tables, QuestieDB answers only the ids the store lacks, the store wins when both have the data, an absent or incompatible QuestieDB changes nothing and is never read, and every id that stays missing after the whole chain ran gets one clear chat message per session. The `options` suite covers the options panel: the window opens through `Options.Open`, shows the saved values for the waypoint toggle, the window lock, the scale, and the opacity, writes every change straight into the account-wide table, and registers itself neither with the client's options windows nor with FlareUI. The `menu` suite covers the small menu beside the step window: it opens through `Menu.Open`, which puts the menu's top left beside the top right of the anchor frame it is handed, or at a fixed screen spot when no anchor is given -- the seam the step window calls, passing itself as the anchor. The suite checks that the skipped quests list by name from the data store and leave both the skip list store and the saved table when a restore is clicked, that a quest missing from the data lists under its id, that the menu says so in plain words when nothing is skipped, that every known dungeon from the dungeon guide table is listed with its level range, and that the options link calls `Options.Open`. The `stepwindow` suite covers the step window: the text it shows for the step on screen -- the headline, the goal lines with their tick boxes and counts, the tips, the place text, the hunts block, the reward names with their hover tooltips, and the next three steps -- with and without a FlareUI fake present, the Back and Next paging with the "Step N / M" line and the way back to the current step, the right-click skip on the step and on the listed next steps, the Follow toggle with the followed step and the click back to the route, hide and show, the drag that writes the saved place and the lock that stops it, the scale and the opacity from the saved table, the menu anchor from the title bar, the current-step and place queries with the changed signal that the later tickets build on, and the promise that no quest action -- accept, hand in, or abandon -- is ever offered. Its scenarios load the code modules by hand into a namespace with its own small quests and Path, on the widget fake the options and menu suites use, and the last part brings the window up on the real copied tables through the shared loader. The `lookadapter` suite covers the look adapter: the copy of the FlareUI tracker's backdrop, colors, and fonts onto the window from a fake of the live tracker frame, the dock below the tracker, the window's own width that the dock never gives up, the drag that stays off while the window is docked, the flat look and the lock-gated drag without FlareUI, the flat fallback without an error when the tracker global is not a frame, has no backdrop, or has no scroll of lines, and the re-apply across refreshes when FlareUI appears late or goes away. Its widget fake registers named frames the way the client does, and the last part loads the real addon through the shared loader with the tracker fake present. The `tomtombridge` suite covers the TomTom bridge: one waypoint per step with the headline as its title and the addon as its setter, no display flags so the TomTom options decide, one session of life with `persistent = false`, the replacement on every step change with the old waypoint off first, the removal when the window hides, when the player skips the quest, and when the route runs dry, the nearest of several candidate places by true yards from the player, no waypoint without coordinates and none inside an instance, the off option in the saved table and the panel toggle that takes a standing waypoint down at once, the promise that the waypoint the player set by hand survives every operation, and the quiet around a missing or fake TomTom, where the step window keeps working. Its scenarios load the code modules by hand as well, and the TomTom fake records every add and remove the bridge makes. The `commands` suite covers the slash commands: `/eq` and `/efficientquests` run the same handler, a bare command toggles the step window, `options` and `config` open the options panel, `status` writes the version, the data snapshot, and one word per optional addon -- found or missing -- both with no optional addon in the world and with FlareUI, TomTom, and QuestieDB fakes present, and also without the client's metadata service, and `help` lists the commands while an unknown word points at it. The `manifest` suite reads the shipped manifest text and the files the manifest lists. It checks the interface number, the version, the optional dependencies, the saved variables, and the embedded libraries, the order of the data files and the data store, and it rejects the pins files and leftover mentions of removed addons.Luacheck checks the addon code in `dist/EfficientQuests` for accidental global variables. The configuration is `.luacheckrc` at the repository root. It names the game services that the addon can use as globals. A global that the list does not name fails the check. The embedded libraries under `dist/EfficientQuests/Libs` and the generated data tables (`QuestData.lua`, `PathData.lua`, `DungeonGuides.lua`) are verbatim copies of third-party code and data, so luacheck skips them.

The CI workflow runs the same Docker commands.

These tests run without the game. They do not show that the addon works in a Forever client, and they do not show how the window looks. The [validation record](../docs/validation.md) tracks the in-client and visual checks.
